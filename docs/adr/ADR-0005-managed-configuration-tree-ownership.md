# ADR-0005: Managed Configuration Tree Ownership

## Status

Accepted

## Context

A FreeRADIUS deployment consists of more than configuration file contents.

Whether a module or virtual server is enabled is determined by the presence of symbolic links such as:

- mods-enabled/sql
- sites-enabled/default

These symbolic links alter the effective behaviour of a running FreeRADIUS instance in the same way as configuration files.

An architectural decision is required to determine whether symbolic links are generated as part of the managed configuration or created later by the deployment layer.

## Decision

The managed configuration tree SHALL represent the complete desired filesystem state for a tenant.

The managed configuration tree SHALL include all managed configuration required for the deployment, including:

- managed configuration files
- managed symbolic links

The deployment layer SHALL materialize the managed configuration tree without generating or modifying configuration.

The deployment layer is responsible for:

- installing the managed configuration tree
- provisioning supporting infrastructure
- starting and updating FreeRADIUS instances

The deployment layer SHALL NOT determine which modules or virtual servers are enabled.

That decision is part of the managed configuration generated by RADIUS Director.

## Consequences

Advantages:

- Complete desired state is represented in one place.
- Rendering fully defines the managed configuration.
- Deployment becomes simpler and deterministic.
- Deployment implementations remain independent of FreeRADIUS configuration details.
- Different deployment targets (Docker, Podman, Kubernetes, virtual machines, bare metal) consume the same managed configuration tree.

Trade-offs:

- The managed configuration tree contains filesystem metadata in addition to file contents.
- Renderers must produce symbolic links where required.

These trade-offs are preferable because they preserve a clear separation between configuration generation and deployment.

## Example

The following managed configuration tree represents the desired filesystem state for a tenant.

```text
customer-a/
├── clients.conf
├── radiusd.conf
├── proxy.conf
├── mods-available/
│   └── sql
├── mods-enabled/
│   └── sql -> ../mods-available/sql
├── sites-available/
│   ├── default
│   └── coa
└── sites-enabled/
    ├── default -> ../sites-available/default
    └── coa -> ../sites-available/coa
```

The deployment layer installs this tree exactly as generated.

It does not decide which symbolic links should exist or modify the generated configuration.
