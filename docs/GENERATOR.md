# Generator

This document describes how RADIUS Director transforms the declarative configuration model into a managed FreeRADIUS configuration tree.

The generator consumes a validated configuration model and produces a deterministic internal representation that is rendered into managed FreeRADIUS configuration.

---

# Design Goals

The generator should be:

- deterministic
- repeatable
- idempotent
- vendor neutral
- standards based

Given the same input configuration, the generator must always produce identical output.

---

# Generation Pipeline

Configuration generation consists of several stages.

```
Read Configuration
        │
        ▼
Parse YAML
        │
        ▼
Build Object Model
        │
        ▼
Resolve References
        │
        ▼
Validate
        │
        ▼
Generate Internal Model
        │
        ▼
Render Managed Configuration
        │
        ▼
Assemble Managed Configuration Tree
        │
        ▼
Write Managed Configuration
```

Each stage must complete successfully before the next stage begins.

---

# Stage 1 - Read Configuration

The generator reads the declarative configuration from one or more YAML files.

No validation is performed at this stage beyond confirming that the files can be read.

---

# Stage 2 - Parse Configuration

The YAML configuration is parsed into the internal object model.

This stage converts configuration into strongly typed objects.

No FreeRADIUS configuration is generated during parsing.

---

# Stage 3 - Resolve References

Object references are resolved.

Examples include:

- NAS Assignments locating NAS Devices
- NAS Assignments locating Credential Profiles
- Tenants locating Databases
- Tenants locating RADIUS Servers

After this stage, the object graph is fully connected.

---

# Stage 4 - Validate

The complete object model is validated.

Generation must stop immediately if validation fails.

Validation rules are described in VALIDATION.md.

---

# Stage 5 - Build Internal Model

The validated object graph is transformed into an internal representation optimized for rendering.

This stage may combine multiple objects into structures that more closely represent the managed FreeRADIUS configuration.

The internal model is an implementation detail and is not part of the public configuration schema.

---

# Stage 6 - Render Managed Configuration

The internal model is rendered into managed FreeRADIUS configuration files.

Renderers operate independently wherever practical.

Each renderer is responsible for producing one logical managed configuration component.

Examples include:

- clients.conf
- radiusd.conf
- proxy.conf
- mods-available/sql
- sites-available/default
- sites-available/coa

Renderers operate only on files managed by RADIUS Director.

Configuration that belongs to the installed FreeRADIUS distribution is not rendered.

---

# Stage 7 - Assemble Managed Configuration Tree

The rendered files are assembled into a deterministic managed configuration tree for a tenant.

The managed configuration tree represents the complete deployment-specific configuration produced by RADIUS Director.

It may include:

- managed configuration files
- symbolic links required to enable managed modules or virtual servers

The managed configuration tree does not include files owned by the FreeRADIUS distribution.

---

# Stage 8 - Write Managed Configuration

The managed configuration tree is written to the configured output directory.

Existing managed files may be replaced.

Files outside the managed configuration boundary must not be modified.

---

# Deterministic Generation

Configuration generation must be deterministic.

The generator should not depend on:

- object insertion order
- filesystem ordering
- map iteration order
- random values

Objects should be generated in a predictable order whenever practical.

---

# Error Handling

Generation must stop if:

- configuration cannot be parsed
- references cannot be resolved
- validation fails
- rendering encounters an unrecoverable error

No partial managed configuration should be written.

---

# Source of Truth

The declarative configuration is the source of truth.

The managed configuration generated by RADIUS Director is an implementation artifact that may be safely regenerated at any time.

Managed configuration should never be edited manually.

---

# Design Philosophy

The generator should remain as simple as possible.

Business logic belongs in the configuration model.

Validation belongs in the validator.

Rendering belongs in the renderer.

Writing files belongs in the writer.

Deployment belongs in the deployment layer.

The generator's responsibility is to transform a valid object model into a deterministic managed configuration model suitable for rendering.
